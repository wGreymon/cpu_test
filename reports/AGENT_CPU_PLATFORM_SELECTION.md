## 一、Agent 执行任务拆解与硬件性能依赖分析

本部分回答一个问题：**Agent 业务到底让 CPU 平台做什么，因此选型应当看重哪些硬件指标。**
这是第二部分全部测试项选取与结果解读的依据。

### 1、Agent 的执行架构：哪些环节落在被测平台上

Agent 由大模型负责推理与决策，再调用工具完成实际动作。完整链路如下：

```text
大模型推理（本地 GPU/NPU，或远端 API）
        │  生成工具调用
        ▼
Agent 调度程序（CPU：解析、编排、状态管理）
        │  创建任务
        ▼
沙箱（进程 / 容器 / gVisor / microVM —— CPU + 内核管理）
        │
        ▼
工具执行（Python / Shell / 编译器 / 检索 / 数据处理 —— CPU 为主）
```

**范围界定（本报告的评估边界）：**

1. **模型推理不计入本机 CPU 评估。** 推理由 GPU/NPU 或远端 API 承担；API 模式下本机只负责构造请求、TLS 通信与解析响应，模型等待时间必须与本地执行时间分开统计。
2. **沙箱的创建、调度、隔离与回收完全由 CPU + 操作系统内核承担**（namespace、cgroup、seccomp、调度器、虚拟化指令），这是"CPU 通算平台"在 Agent 业务中的核心角色。
3. GPU 仅在沙箱内任务显式需要加速计算时参与，属于可选路径，不在本轮对比范围。

Agent 的运行是一个循环：接收目标 → 模型推理规划 → 选择工具 → **沙箱内执行 → 读取结果** → 判断是否完成 → 下一轮。加粗环节每轮都发生、频率最高，其效率由本机 CPU/OS/内存决定——这就是选型的评估对象。

### 2、Agent 任务分类与硬件依赖逐项分析

按执行内容将 Agent 的本机负载拆为十类。每类给出：做什么、走什么硬件路径、对什么指标敏感。

#### 2.1 Agent 编排（每轮循环必经）

解析模型返回的 JSON/结构化输出、管理上下文与任务状态、调度子任务、控制重试与超时、记录日志。
**特征**：计算量小、操作极频繁、持续时间短。
**硬件依赖**：单核标量性能（响应速度）、缓存与内存延迟（大量短操作）、多核与调度（多 Agent 并发编排）。

#### 2.2 与模型服务端通信（API 模式）

建立 HTTPS 连接、TLS 加解密、上传上下文、接收流式 Token、管理连接池与并发请求。
**硬件依赖**：CPU 加密性能（AES/SHA 硬件指令）、高并发连接处理；网络 RTT 属于环境因素。远端推理时间不计入本机性能。

#### 2.3 代码/文件检索

`rg`、`find`、`git status/diff/log`，遍历仓库、读取大量小文件、解析与匹配。
**硬件依赖**：单核整数性能、缓存与内存延迟（热数据在页缓存时检索是纯 CPU+内存负载）、存储小文件随机读（冷数据）。

#### 2.4 Shell 短命令执行

Agent 高频调用 `ls/grep/sed/awk/git/curl` 等短命令。每条命令都经历：**fork/exec → 动态库加载 → 系统调用 → 管道通信 → 上下文切换 → 结果收集**。
**硬件依赖**：进程创建延迟、系统调用延迟、上下文切换开销、单核性能。
这是微基准中 lmbench / hackbench / perf bench 与 Agent 场景强相关的直接原因。

#### 2.5 生成并运行代码

以 Python 为典型：解释器冷启动、导入依赖、执行文本/JSON 处理逻辑；少数任务涉及数值计算或图像处理。

| 代码任务类型 | 主要硬件依赖 |
|---|---|
| Python 启动与导包 | 单核、内存延迟、小文件 I/O |
| JSON/文本/日志处理 | 单核整数、缓存、内存 |
| 数值计算（NumPy 等，少数） | SIMD、多核、内存带宽 |
| 数据库查询（SQLite 等） | 单核、内存、存储延迟 |

#### 2.6 编译与测试

`gcc/cargo/npm install/pytest/make test`：安装依赖、并行编译、运行测试、读错误、改代码、重复。
**硬件依赖**：单核（串行编译阶段与增量小编译）、多核扩展性（并行编译）、进程创建与调度（编译器进程风暴）、内存容量与带宽（大项目构建）、小文件 I/O 与解压哈希（依赖安装）。
这是评价平台对 Coding Agent 支持能力的重点负载。

#### 2.7 数据处理类工具任务

压缩/解压（zstd/7z）、哈希与签名校验（sha256/RSA）、图像转换、本地数据库导入查询。
**硬件依赖**：整数吞吐、硬件加密指令、内存带宽、多核。

#### 2.8 沙箱生命周期管理（平台方的核心开销）

每次工具执行前后，Agent 平台要：创建进程/容器/microVM → 准备根文件系统与挂载 → 配置 namespace/cgroup/seccomp → 施加 CPU/内存/进程数/时间限制 → 执行并收集 stdout/stderr/退出码 → 终止超时或 OOM 任务 → 销毁并回收。
**硬件依赖**：进程创建、系统调用、上下文切换（内核路径三件套）、页表与缺页处理、存储镜像读取；microVM（Firecracker/Kata）额外依赖 KVM、EPT/NPT 与虚拟化切换性能。

#### 2.9 多 Agent / 多沙箱并发（决定单机业务容量）

数十至数百个沙箱同时运行时，平台表现取决于：
**核数与多核扩展效率**（任务并行执行）、**调度器高压吞吐**（海量任务频繁阻塞/唤醒）、**核间通信与拓扑**（任务迁核、锁竞争代价）、**内存带宽在负载下的延迟表现**（所有沙箱共享内存子系统——带宽压力上来后延迟是否失控，直接决定并发密度上限）、**NUMA 特性**（跨节点访问惩罚决定是否必须绑核部署）、**内存容量**（每沙箱 RSS × 并发数）。

#### 2.10 长时间运行的稳定性

持续满载下的降频行为（性能是否随时间衰减）、反复创建销毁下的资源回收、能耗效率（数据中心成本）。

**可选负载**（仅在沙箱实际配置对应工具时纳入）：浏览器操作（Chromium，高 RSS，主要限制并发密度）、本地向量检索/Embedding（SIMD 与内存带宽；若由远端服务提供则不计入本机）。

### 3、从任务归纳硬件能力维度

十类任务的依赖收敛到四个硬件能力维度，权重如下：

| 维度 | 覆盖的 Agent 任务 | 选型权重 | 理由 |
|---|---|---|---|
| **系统能力**（系统调用、进程创建、上下文切换、调度器） | Shell 短命令、沙箱生命周期、多沙箱并发，及所有任务的执行入口 | **最高** | 沙箱创建/销毁和短命令执行全部走内核路径，且频率随并发线性放大；seccomp/gVisor 等隔离层会进一步放大此路径开销 |
| **CPU 核心能力**（单核标量、多核扩展、核间通信、持续性能、能效） | Agent 编排、代码检索、运行代码、编译测试、数据处理、长时稳定 | 高 | 单核决定单任务响应速度，多核扩展与核间拓扑决定整机吞吐上限 |
| **内存能力**（延迟、带宽、负载下延迟、NUMA、容量） | 代码检索、运行代码、编译测试、多沙箱并发 | 高（并发场景关键） | 解释器、编译、检索均是内存敏感负载；**负载下延迟（loaded latency）在高并发时决定所有任务的实际内存访问成本** |
| 存储 I/O（辅助） | 检索、运行代码、编译测试的冷数据路径 | 低（解释用） | 小文件与镜像读取影响端到端，但存储硬件独立于 CPU 平台，不参与平台排名 |
| 浮点/SIMD | 运行代码中的少数数值计算任务 | 最低 | Agent 负载以整数、内存、内核路径为主，仅作可选参考 |

网络能力属于环境因素（同机房内取决于网卡而非 CPU 平台），记录但不参与选型。

### 4、任务 → 硬件指标 → 测试项映射表（本报告的分析枢纽）

第二部分的每项实测结果，通过此表回溯到 Agent 业务含义（各测试的具体命令、参数与判定标准见 `PART1_TEST_SPEC.md`，其中的测试编号与本表的测试名称一一对应）：

| Agent 任务 | 关键硬件路径/指标 | 对应测试（所用工具） |
|---|---|---|
| Agent 编排 | 单核标量、缓存/内存延迟 | 单线程计算基准（sysbench、7-Zip）；缓存/内存延迟阶梯（lat_mem_rd） |
| API 通信加密 | AES/SHA 硬件指令吞吐 | 加密/哈希吞吐（OpenSSL speed） |
| 代码检索 | 单核整数、内存延迟、小文件读 | 单线程计算基准；延迟阶梯；存储小文件与随机读（fio） |
| Shell 短命令 | fork/exec、系统调用、上下文切换 | **系统调用延迟、进程创建延迟、上下文切换开销（lmbench，perf bench 交叉验证）** |
| Python 启动导包 | 进程创建、内存延迟、小文件 | 进程创建延迟（lmbench + 千次短进程实测）；延迟阶梯；小文件读 |
| 编译构建 | 单核+多核扩展、进程创建、内存带宽 | 单线程/多线程计算基准与扩展效率曲线；进程创建延迟；内存带宽（STREAM） |
| 单元测试 | 进程调度、单核 | 进程创建延迟；调度器压力（hackbench）；单线程计算基准 |
| 压缩/哈希工具任务 | 整数吞吐、硬件指令 | 压缩/解压吞吐（zstd，固定 Silesia 数据集）；加密/哈希吞吐（OpenSSL） |
| 沙箱生命周期 | 内核路径三件套、调度压力 | **系统调用、进程创建、上下文切换微基准 + 调度器压力（hackbench）** |
| 高并发沙箱密度 | 多核扩展、核间延迟、负载下内存延迟、NUMA、带宽扩展 | **多线程扩展效率；核间通信延迟矩阵（core-to-core-latency）；负载下内存延迟（MLC loaded latency）；NUMA 延迟/带宽矩阵（MLC、numactl）；多线程带宽扩展（STREAM）** |
| 长时稳定与成本 | 持续吞吐衰减、整机能效 | 一小时持续满载与降频观测（stress-ng + turbostat）；整机功耗与能效（BMC 采样） |
| 系统综合参考 | 整机系统表现 | 系统综合基准（UnixBench，仅作参考） |

三处加粗是 Agent 沙箱场景区别于传统服务器选型的特征所在：**内核路径微基准（系统调用/进程创建/上下文切换/调度压力）和负载下内存延迟的权重，远高于传统跑分场景。**

### 5、测试方法论要点（详见 PART1_TEST_SPEC.md V0.3）

1. **两类测试、两种角色**：平台基础微基准（本轮已执行）用于解释能力与瓶颈来源；Agent 真实负载测试（后续阶段）分"固定动作回放"（严格可比，作排名依据）与"完整 Agent 任务"（真实性验证）两种模式。
2. **有效性控制**：每项预热 ≥2 次、正式 ≥5 次；计算类 CV ≤3%、系统类 ≤5%；两平台差异小于 2× 合并 CV 判为持平；环境（内核、governor、SMT）保持一致，mitigations 跨厂商采用各自生产默认策略并记录解释。
3. **报告口径**：整机吞吐类同时报告整机与每核结果；延迟、单线程、带宽类不做每核归一化；不将各维度合成单一总分。
4. **本轮结论的限定**：第二部分基于"与 Agent 任务强相关的微基准"作选型推断；Agent 真实任务集与沙箱开销的直接测量属于下一阶段，两者结论将相互印证。

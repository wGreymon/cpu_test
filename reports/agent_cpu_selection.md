# Agent 任务的 CPU 通算平台选型报告

本文面向使用远程大模型 API 的 Agent，分析 Agent 在本地执行的任务及其硬件需求，并据此比较两个 CPU 通算平台。报告分为三部分：

1. Agent 执行任务与硬件需求分析。
2. 两个通算平台的测试结果与选型分析。
3. 真实 Agent 评测与行为仿真。

# 1 Agent 执行任务与硬件需求分析

## 1.1 研究范围与 Agent 执行流程

本文所说的 Agent，是指由大模型驱动、能够持续调用工具完成任务的程序，例如 Coding Agent、Terminal Agent、数据分析 Agent 和浏览器 Agent。

本报告主要研究调用远程大模型 API 的 Agent。大模型推理发生在远端服务端，不计入本地 CPU 性能；本地平台负责 Agent 框架运行、请求与响应处理、工具调度以及具体任务执行。模型 API 延迟属于端到端任务时间，但不应被解释为本地 CPU 的性能差异。

远程 API 模式并不意味着本机完全没有通信开销。本地仍需建立或复用 HTTPS 连接、执行 TLS 加解密、上传上下文、接收流式响应，并维护连接池和并发请求。TLS、序列化和响应解析会消耗少量 CPU；网络 RTT、服务端排队和模型生成时间则属于外部因素，二者应分开记录。

Agent 的典型执行流程为：

```text
接收任务目标
    ↓
读取上下文与运行环境
    ↓
调用远程大模型进行规划
    ↓
解析模型返回的工具调用
    ↓
在本地执行命令、代码或其他工具
    ↓
收集并处理执行结果
    ↓
判断任务是否完成
    └── 未完成：将结果加入上下文并进入下一轮
```

一个完整 Agent 任务可能包含多轮模型请求和数十至数百次本地工具调用。因此，本地平台既要保证单次工具调用足够快，也要能够稳定承载多个 Agent 并发运行。

## 1.2 Agent 编排与状态管理

在模型调用前后，Agent 框架需要完成：

- 组织用户目标、历史消息、工具描述和环境信息。
- 构造模型 API 请求并解析返回结果。
- 管理 HTTPS 连接、TLS 通信、流式响应和并发请求。
- 编码、解码和校验 JSON 等结构化数据。
- 解析模型生成的工具调用参数。
- 管理上下文、任务状态、日志和执行轨迹。
- 处理超时、取消、重试与错误恢复。
- 调度多个工具、子任务或并行 Agent。

这类操作的单次计算量通常不大，但会在 Agent 循环中频繁发生。其代码通常包含大量条件判断、字符串处理、哈希、地址计算和动态数据结构访问，属于延迟敏感的串行负载。

主要硬件依赖：

- **CPU 单核性能**：影响一轮编排与结构化数据处理的延迟。
- **整数与分支处理能力**：影响 JSON、字符串、日志和状态处理。
- **缓存与内存延迟**：影响对象、哈希表、队列和任务状态访问。
- **操作系统调度能力**：影响异步工具调用和多 Agent 并发。
- **加密与哈希能力**：影响大量并发 HTTPS 连接的 TLS 处理。
- **网络延迟**：影响远程模型请求，但属于外部因素，不是本地 CPU 成绩。

这里的“整数性能”不只是整数数学运算，还包括地址计算、条件判断、循环、字符串扫描、哈希、位运算和指针访问。这些操作广泛存在于解释器、JSON 解析器和系统工具中。

## 1.3 文件与代码仓库操作

Coding Agent 为了理解和修改项目，通常会执行：

```bash
find . -type f
rg "keyword"
git status
git diff
git log
```

更复杂的代码理解还可能包括：

- 遍历目录并读取大量小文件。
- 搜索符号、定义和引用。
- 解析源代码并建立抽象语法树。
- 建立或查询代码索引。
- 计算文件差异、哈希和版本状态。
- 读取、修改和写回项目文件。

这类任务不是单纯的 CPU 计算负载。文本扫描、正则表达式和语法解析依赖 CPU；目录遍历和小文件访问还会受到页缓存、文件系统元数据和存储设备影响。

主要硬件依赖：

- **CPU 单核与整数性能**：影响文本扫描、正则表达式、语法解析和 Git 操作。
- **缓存与内存延迟**：影响目录树、代码索引和语法树访问。
- **文件系统元数据性能**：影响 `stat`、`open`、`close` 和目录遍历。
- **小文件随机读取性能**：影响仓库扫描和代码加载。
- **存储吞吐**：当仓库规模超过页缓存时，影响全量读取速度。

## 1.4 命令调用与脚本执行

Agent 会频繁调用 Shell 和外部工具，例如：

```bash
ls
grep
sed
awk
git
curl
python
```

每次短命令都会经历进程创建、程序加载、动态链接、系统调用、管道通信、上下文切换、进程退出和资源回收。对于执行时间很短的命令，这些固定开销可能比命令本身的计算时间更重要。

Agent 还可能生成并运行 Shell、Python 或 JavaScript 脚本。解释器启动、Python 导包和依赖加载会执行串行初始化逻辑，并访问大量小文件。

主要硬件依赖：

- **进程创建性能**：影响 `fork/exec` 和解释器启动速度。
- **系统调用与上下文切换性能**：影响短命令和管道通信。
- **CPU 单核性能**：影响脚本解析及串行执行。
- **缓存与内存延迟**：影响解释器和运行时对象访问。
- **文件系统元数据与小文件读取**：影响程序加载和依赖导入。
- **调度器性能**：影响多个工具同时执行时的延迟与公平性。

## 1.5 编译、构建、依赖安装与测试

Coding Agent 修改代码后，通常会反复执行：

```bash
make
cmake --build
cargo build
npm install
pytest
make test
```

一个代码修复任务可能经历多轮“检索—修改—编译—测试—分析错误—再次修改”。因此，构建与测试速度会直接影响 Agent 完成任务的总时间。

编译同时包含串行和并行阶段。预处理、语法解析、模板实例化和链接等阶段可能受单核性能限制；多个源文件并行编译则能够利用更多核心。依赖安装还会引入网络下载、压缩包解压、哈希校验和大量小文件写入。

主要硬件依赖：

- **CPU 单核性能**：影响串行编译和链接阶段。
- **CPU 多核吞吐与扩展效率**：影响并行编译和并行测试。
- **整数、分支和缓存性能**：影响编译器前端与代码生成。
- **内存容量和带宽**：影响大型项目及高并发构建。
- **文件系统和小文件 I/O**：影响源码读取、依赖安装和中间文件生成。
- **进程创建与调度能力**：影响大量测试进程的启动和运行。
- **压缩、解压与哈希能力**：影响软件包和构建制品处理。

## 1.6 数据处理、数据库与浏览器任务

除代码开发外，通用 Agent 还可能执行多种本地任务。

### 1.6.1 文本与结构化数据处理

典型操作包括 JSON、XML、CSV、日志和配置文件处理，以及字符串匹配、正则表达式、过滤、排序和聚合。

主要依赖：

- CPU 单核、整数和分支处理能力。
- 缓存与内存访问延迟。
- 大数据扫描时的内存带宽。
- 数据文件的存储吞吐。

### 1.6.2 数值与数组计算

Python、NumPy 或其他数据分析工具可能执行数组、矩阵和统计计算。

主要依赖：

- CPU 浮点与 SIMD 性能。
- 多核计算能力。
- 内存带宽和缓存容量。

### 1.6.3 数据库和 RAG 检索

Agent 可能进行文档切分、全文索引、本地数据库查询、向量检索和结果排序。如果 Embedding 由远程 API 生成，本地平台只承担文档处理、索引和检索；如果在本地生成，则需要单独考虑 AI 推理负载。

主要依赖：

- 文档解析所需的单核和整数性能。
- 索引所需的内存容量和小文件 I/O。
- 向量检索所需的 SIMD、缓存和内存带宽。
- 数据库查询所需的随机 I/O、锁与调度能力。

### 1.6.4 浏览器自动化

浏览器 Agent 可能启动 Chromium、加载页面、执行 JavaScript、解析 DOM、截图以及上传或下载文件。现代浏览器采用多进程架构，单个实例的内存占用通常明显高于命令行工具。

主要依赖：

- CPU 单核与多核性能。
- 进程调度与进程间通信能力。
- 内存容量、缓存和内存带宽。
- 图片编解码所需的 SIMD 性能。
- 网络性能以及可选的 GPU 图形加速。

## 1.7 沙箱与多 Agent 并发

为了隔离模型生成的代码，Agent 平台可能使用受限进程、容器、gVisor 或 microVM。其运行过程可能包括：

- 创建进程、namespace、cgroup 或虚拟机。
- 准备根文件系统并挂载工作目录。
- 设置 CPU、内存、进程数和网络限制。
- 应用 seccomp 等系统调用安全策略。
- 执行命令并收集标准输出、错误和退出码。
- 终止超时任务，并在 OOM 或异常退出后回收资源。

主要硬件依赖：

- 进程创建、系统调用和上下文切换性能。
- 页表、内存映射、缺页和写时复制性能。
- 文件系统与镜像层的存储访问性能。
- 每个隔离实例所需的额外内存容量。
- 多核调度和高并发资源回收能力。
- microVM 所需的 KVM、EPT/NPT 等硬件虚拟化能力。

当前尚未确定统一的 Agent 沙箱实现，因此暂不把某一种沙箱方案作为 CPU 平台的强制测试项。后续应在技术方案明确后，对比同一任务在裸机和目标沙箱中的启动、执行、销毁及资源占用。

生产环境通常会并发运行多个 Agent。随着并发数增加，编排线程、Shell 进程、编译器、测试进程和浏览器实例会共同竞争 CPU、内存与 I/O 资源。

多 Agent 并发主要依赖：

- **物理核心数和整机吞吐**：决定同时处理任务的基础能力。
- **调度器扩展能力与公平性**：决定任务竞争时的响应稳定性。
- **核间通信与 CPU 拓扑**：影响任务迁移、共享队列、锁竞争和跨核数据传递。
- **内存容量和带宽**：决定可承载的 Agent 数量和数据访问效率，容量需求近似为单 Agent 实际 RSS 与并发数的乘积，再加平台公共开销和安全余量。
- **负载下内存延迟**：并发任务接近内存带宽上限时，访问延迟可能迅速上升，进而同时拖慢所有 Agent。
- **NUMA 架构**：跨节点访问可能增加延迟并降低有效带宽。
- **存储并发能力**：影响多个任务同时检索、构建和写入文件。
- **持续频率、功耗和散热**：影响长时间满载下的真实吞吐。

评价多 Agent 场景时，除平均完成时间外，还需要关注整机吞吐、P95/P99 延迟、失败率、性能波动和单任务资源消耗。

沙箱还需要考察长期资源回收是否可靠。反复创建和销毁沙箱后，如果遗留进程、挂载点、文件、页缓存或内存占用，平台的可用并发密度会随运行时间下降；这类问题不能由一次启动延迟测试发现。

## 1.8 Agent 任务与硬件能力对应关系

Agent 的本地负载可以归纳为四类平台能力：

1. **OS 能力**：进程创建、系统调用、上下文切换、进程通信和调度。
2. **CPU 计算能力**：单核、多核、整数、浮点、SIMD、压缩、哈希和加密。
3. **内存与 I/O 能力**：缓存、内存延迟、内存带宽、NUMA、文件系统和存储。
4. **持续性能**：长时间运行频率、温度、功耗、吞吐保持率和稳定性。

具体对应关系如下：

| Agent 任务 | 主要负载特征 | 主要硬件依赖 |
|---|---|---|
| 编排、JSON 和状态管理 | 短小、串行、分支密集 | CPU 单核、整数、缓存、内存延迟 |
| API 请求与流式响应 | HTTPS、TLS、序列化、连接池 | 加密/哈希、单核、网络与并发连接处理 |
| 高频 Shell 命令 | 大量短进程和系统调用 | 进程创建、系统调用、上下文切换、调度 |
| 代码和文本检索 | 文本扫描、大量小文件 | CPU 单核、缓存、文件系统、小文件 I/O |
| Python 启动与导包 | 串行初始化、元数据访问 | CPU 单核、内存延迟、文件系统元数据 |
| 编译与构建 | 串并行计算、小文件访问 | CPU 单核/多核、内存容量和带宽、I/O |
| 单元测试 | 多进程与实际业务代码 | OS 调度、CPU、内存、存储 |
| JSON、日志和数据处理 | 整数、分支、内存访问 | CPU、缓存、内存延迟和带宽 |
| 数值和数组计算 | 浮点、向量和流式访问 | 浮点、SIMD、多核、内存带宽 |
| 压缩、解压和哈希 | 位运算、SIMD、流式访问 | CPU 单核/多核、SIMD、内存带宽 |
| 数据库和向量检索 | 随机访问、缓存、锁竞争 | 内存、SIMD、调度、存储 IOPS |
| 浏览器自动化 | 多进程、JavaScript、大内存 | CPU、OS 调度、内存容量、网络 |
| 沙箱创建与销毁 | 内核、文件系统、虚拟化 | OS、内存、存储、硬件虚拟化 |
| 多 Agent 并发 | 多任务竞争、大工作集 | 核数、调度、核间通信、负载下内存延迟、NUMA、内存容量、I/O |
| 长时间运行 | 持续混合负载 | 持续频率、散热、功耗和稳定性 |

平台选型还需要区分两个不同目标：

- **单 Agent 响应速度**主要取决于单核性能、短进程启动、系统调用、缓存和小文件访问。
- **多 Agent 并发能力**主要取决于物理核心数、整机吞吐、调度能力、内存容量、NUMA 和存储并发能力。

存储和网络结果需要与 CPU 结果分开归因。两台机器使用不同磁盘、文件系统、网卡或网络路径时，相应差异不能直接归因于 CPU；正式比较应尽量统一环境，无法统一时则将其作为平台整体能力或外部限制单独说明。

因此，不存在一个单独的 CPU 跑分能够完整代表 Agent 性能，也不宜在真实业务权重尚未获得时预先给各项能力设定固定权重。后续应先用基础微基准解释能力差异，再用步骤和数据完全一致的 Agent 行为回放进行可比验证，最后用完整 Agent 任务确认实际效果；完整 Agent 测试中还应把模型/API 等待时间与本地执行时间分开统计。

# 2 两个通算平台的测试结果与选型分析

> 待两个候选平台完成正式测试后补充。本部分将记录平台配置、测试条件、具体结果、差异原因以及针对不同 Agent 场景的选型结论。

## 2.1 测试工具与能力项预览

本次测试不使用单一综合跑分代表 Agent 性能，而是分别测量 OS 能力、CPU 计算能力、数据访问能力以及持续性能与能效。同一能力项在 Intel 和 AMD 平台上必须保持测试目标和输出指标一致；横向排名优先使用两平台共同支持的工具，厂商专属工具仅用于补充解释。

| 能力类别 | 工具 | 本次负责的测试内容 | 主要输出 | 平台适用性 |
|---|---|---|---|---|
| OS 能力 | UnixBench | 系统综合的单副本与 16 副本表现（不用于高核数整机扩展性） | 综合指数 | Intel/AMD 共同测试 |
| OS 能力 | lmbench `lat_syscall` | `null`/`read`/`write` 系统调用延迟 | 微秒/次 | Intel/AMD 共同测试 |
| OS 能力 | lmbench `lat_proc` + `proc_spawn.py` | `fork`/`exec`/Shell 启动及 1000 次短进程创建 | 延迟、P95 | Intel/AMD 共同测试 |
| OS 能力 | lmbench `lat_ctx` + `perf bench sched` | 不同进程数与工作集下的上下文切换和调度延迟 | 微秒/次 | Intel/AMD 共同测试 |
| OS 能力 | hackbench | 常规和过载并发下的调度器与进程通信能力 | 完成时间 | Intel/AMD 共同测试 |
| CPU 计算 | sysbench CPU + 7-Zip Benchmark | 单线程通用计算、多线程整机吞吐与扩展效率 | events/s、MIPS | Intel/AMD 共同测试 |
| CPU 计算 | zstd + Silesia 固定数据集 | 快速档和高压缩档的单核/多核压缩与解压 | MB/s、压缩率 | Intel/AMD 共同测试 |
| CPU 计算 | OpenSSL `speed` | SHA-256、AES-256-GCM 和 RSA-2048 的哈希、加密和签名能力 | MB/s、sign/s、verify/s | Intel/AMD 共同测试 |
| CPU 计算 | core-to-core-latency | 物理核两两通信延迟及跨 socket/跨拓扑边界代价 | 延迟矩阵（ns） | Intel/AMD 共同测试 |
| 数据访问 | memtester + EDAC | 分 NUMA 节点的内存正确性抽样与 ECC 计数变化 | 错误数、CE/UE | Intel/AMD 共同门槛 |
| 数据访问 | STREAM | 单线程、多线程及 NUMA 节点组合下的顺序内存带宽 | Copy/Scale/Add/Triad GB/s | Intel/AMD 共同测试 |
| 数据访问 | lmbench `lat_mem_rd` + numactl | 缓存—内存延迟阶梯，以及本地/远端 NUMA 访问延迟 | 延迟曲线、ns | Intel/AMD 共同测试 |
| 数据访问 | pointer_chase + tinymembench | 超过最大 LLC 的大工作集随机访问，以及 cache/TLB 辅助曲线 | ns/访问 | Intel/AMD 共同测试 |
| 数据访问 | Intel MLC | 空闲延迟、NUMA 延迟/带宽矩阵、峰值带宽和负载下延迟 | ns、GB/s、带宽—延迟曲线 | Intel 专属补充，不单独用于跨平台排名 |
| 数据访问 | fio | 4 KiB 随机读与 1 MiB 顺序读，用于解释 Agent 文件 I/O 差异 | IOPS、MB/s、P95/P99 | Intel/AMD 共同测试，不归因为纯 CPU 性能 |
| 持续性能与能效 | stress-ng + sysbench | 长时间满核负载，并比较压力前后吞吐保持率 | bogo ops/s、events/s、保持率 | Intel/AMD 共同测试 |
| 持续性能与能效 | turbostat + BMC/IPMI | 长时负载中的频率、温度和整机功耗，以及空闲/负载能效 | MHz、°C、W、每瓦吞吐 | 两平台使用各自可用的功耗接口 |
| 辅助分析 | `perf stat` | 在主成绩之外采集周期、指令、缓存失效和上下文切换等计数器 | 硬件/软件事件计数 | Intel/AMD 共同辅助数据 |

其中，Intel MLC 提供的负载下内存延迟目前尚无完全等价的 AMD 工具。为保证能力项对齐，最终横向分析前应在两个平台上补充同一协议的跨平台“后台内存带宽负载 + pointer chase 延迟”测试；MLC 结果只作为 Intel 平台的诊断证据。CPU 浮点/SIMD 专项本轮暂未实施，因此不在本次已用工具中列出；如后续 Agent 工作负载包含本地数值计算，再补充统一的 DGEMM 或同类基准。
